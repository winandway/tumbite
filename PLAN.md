# Plan: Divoox Flex — Fase 3 (automatización, integraciones, optimización y piloto)

Rama `fase-flex-3` sobre `fase-flex-2` (713e6e8bd). Sin producción, sin cobros, sin Stripe Connect para Flex, sin Deliveries para clientes. Se reutiliza el reloj existente (GitHub Actions → `/datos/reloj` → `TAREAS_RELOJ`); no se crea otro. (Las Fases 1 y 2 terminaron con todos sus pasos marcados; sus informes son `docs/DIVOOX-FLEX-FASE-1-RESULTADOS.md` y `docs/DIVOOX-FLEX-FASE-2-RESULTADOS.md`.)

- [x] Paso 1: Verificación inicial — resultado de staging de la Fase 2, git limpio, rama nueva.
- [x] Paso 2: Esquema — bandeja de eventos de salida (`flex_eventos`, llenada por disparadores de la base desde la custodia, las rutas y las incidencias, en la misma transacción), destinos de integración (`flex_webhooks`, `flex_webhook_entregas`, `flex_webhook_intentos`), avisos sin duplicar (`flex_avisos`), políticas de retención y registro de limpiezas (`flex_retencion`, `flex_limpiezas`), capacidad de vehículos de Flex (`flex_capacidad_vehiculo`, sin tocar `vehiculos` de Comida). Pruebas del esquema.
- [x] Paso 3: Compartido — optimizador puro (vecino más cercano + mejora 2-opt, ventanas horarias, paradas obligatorias, distancia en línea recta marcada como estimada, sin inventar tiempos) y capacidad (valores de referencia por tipo de vehículo, marcados como estimados; avisos de exceso y de datos desconocidos). Pruebas.
- [x] Paso 4: Servidor · reloj — vencimiento automático de ofertas (libera paquetes y reserva, avisa a la empresa, deja evento, idempotente), aviso de oferta por vencer, despacho de integraciones y limpieza; todo como tareas del reloj existente, aisladas.
- [x] Paso 5: Servidor · avisos al celular — conductor (oferta, asignación, oferta por vencer, oferta retirada, ruta cancelada, reintento autorizado) y empresa (aceptada, rechazada, iniciada, incidencia, entregas terminadas, devolución pedida, cerrada); idempotentes, sin datos personales, en el idioma de cada persona.
- [x] Paso 6: Servidor · integraciones salientes — alta con validación anti-SSRF (solo HTTPS, sin IP privadas ni nombres internos, DNS seguro, sin redirecciones), secreto cifrado (se muestra una vez), firma HMAC con marca de tiempo e id único, cola con reintentos y espera creciente, registro de intentos, desactivación automática, botón de prueba, rotación del secreto con periodo de gracia, aislamiento entre empresas.
- [x] Paso 7: Servidor · optimización y capacidad — sugerir orden (nunca sobre una ruta activa), aplicar solo antes de salir, comprobar capacidad antes de asignar u ofrecer (aviso y confirmación), capacidad editable por la empresa.
- [x] Paso 8: Servidor · retención y operaciones — políticas por país y servicio, simulación obligatoria antes de ejecutar, las pruebas de entrega jamás se borran sin política aprobada; indicadores de operación sin datos financieros.
- [x] Paso 9: Pruebas del servidor — todos los casos obligatorios (vencimiento, carreras, avisos sin duplicar, firma, SSRF, reintentos, desactivación, aislamiento, optimizador, capacidad, retención), regresión de Comida y de dinero.
- [x] Paso 10: Panel — pantalla de operaciones con indicadores, integraciones (destinos, prueba, rotación, intentos), sugerencia de orden en el detalle de la ruta, aviso de capacidad al asignar, capacidad de vehículos. Pruebas de interfaz.
- [x] Paso 11: App Divoox Driver — tocar un aviso de Flex abre «Mi ruta» en esa ruta; textos es/en.
- [x] Paso 12: Escalabilidad — medición con 10, 100 y 1000 empresas y rutas de 40 y 150 paquetes; resultados y límites.
- [x] Paso 13: Documentos — protocolo de prueba en celulares reales (Android e iOS) y ruta piloto de 20 a 40 paquetes; cuentas de revisores resueltas o documentadas; referencia técnica de la API (integraciones); guías públicas es/en.
- [x] Paso 14: `npm run verify` completo, typecheck de las apps, recorrido en pantalla del panel.
- [x] Paso 15: `docs/DIVOOX-FLEX-FASE-3-RESULTADOS.md` (18 secciones), `CANDADOS.md`, `PENDIENTES.md`; commit; push de la rama (solo staging); informe y detenerse a esperar la Fase 4.
